2R1 Theme Mode and Personalization

You are right that they overlap — but it is worse than duplication. They both write document.documentElement[data-theme], and only one of them survives a reload.

What each control does today

ControlOptionsStored asWrites
Settings → Theme ModeLight · Dark · Systemsra_themedata-theme + .dark
Personalization → UI ThemeLight · Dark · Cyberpunk · Industrialapp_user_preferences.themedata-theme + .dark

Light and Dark are offered twice. Cyberpunk and Industrial only exist in one of them, and System only in the other — so neither control is complete on its own.

Observed behaviour

Traced in the running build, starting from Personalization = Cyberpunk:

start: Personalization = cyberpunk data-theme=cyberpunk accent=#f05 prefs=cyberpunk themeMode=system press Theme Mode = Light data-theme=light accent=#006d77 prefs=cyberpunk themeMode=light reload data-theme=cyberpunk accent=#f05 prefs=cyberpunk themeMode=light

Theme Mode repaints the app and persists themeMode=light — but it never touches prefs.theme. On the next load Personalization re-applies Cyberpunk and the user's Theme Mode choice is silently discarded, while the Theme Mode control still shows "Light" as selected.

The failure a user actually hits

Pick Cyberpunk. Later, switch Theme Mode to Light because the room is bright. The app turns light — it looks like it worked. Reopen the app the next morning and it is Cyberpunk again, with Settings still claiming Light is selected. Nothing tells them why.

Options

Option A — recommended

One control: UI Theme, with System added

Delete the Theme Mode section. Add System as a fifth option under Personalization → UI Theme, so it becomes Light · Dark · System · Cyberpunk · Industrial.

Nothing is lost, the ambiguity is gone, and Settings gets shorter. Needs a one-time migration for users whose only stored preference is sra_theme.

Option B

Two controls with a real hierarchy

Theme Mode picks light/dark/system; Personalization picks a skin within that. Requires light and dark variants of Cyberpunk and Industrial — four new palettes.

More expressive, considerably more work, and the four palettes would each need their own contrast pass.

Why A. Cyberpunk and Industrial are complete palettes, not tints — a "light Cyberpunk" is a new design, not a toggle. Option B multiplies the surface that R4 is already trying to fix. Option A can ship this week; B is a project.

3R2 Wallpaper names

The shoe model names are already in the code. The UI cannot reach them.

// src/constants/wallpapers.ts — name and key disagree
{ id: '...', name: 'Believe That 1',      key: 'personalization.bg.sunset'  }
{ id: '...', name: 'Samba OG',            key: 'personalization.bg.nebula'  }
{ id: '...', name: 'Adistar Control 5',   key: 'personalization.bg.emerald' }

// src/i18n/index.ts — the keys still hold the pre-rebrand labels
"personalization.bg.sunset":  "Sunset"  / "Hoàng hôn"
"personalization.bg.nebula":  "Nebula"  / "Tinh vân"
"personalization.bg.emerald": "Emerald" / "Lục bảo"

// src/components/SettingsPanel*.tsx — the render site
{t(opt.key) || opt.name}

Why the fallback never fires

t() ends in dict[key] || fallback[key] || key — when a key is missing it returns the key string itself, which is truthy. So t(opt.key) || opt.name can never fall through to opt.name, even if the translation were deleted. The model names are unreachable code, and the UI shows "Sunset / Nebula / Emerald" instead.

Proposal

Shoe model names are proper nouns — "Samba OG" is "Samba OG" in every language, so i18n is the wrong home for them. Drop key from the model wallpapers and render name directly, keeping a translated label only for the built-in "Default" swatch:

// wallpapers.ts — model entries carry a name, no i18n key
{ id: '...', name: 'Samba OG' }

// render site — translate only when there is a key to translate
- {t(opt.key) || opt.name}
+ {opt.key ? t(opt.key) : opt.name}

Two smaller things in the same area, worth folding in:

  • The four stale personalization.bg.* entries can then be removed from all four locales.
  • User-added wallpapers (the "saved" gallery) have no label at all — just a thumbnail and a delete button. A simple "Ảnh 1, Ảnh 2…" index, or letting the user name them on save, would make the gallery navigable. Flagging rather than assuming — say if you want it.

4R3 More effects

Four effects exist today. Before adding more, there is a cost issue worth deciding on.

What exists

none · particles · liquid · aurora · waves — all canvas-drawn in BackgroundCanvas.tsx.

The animation loop never stops

BackgroundCanvas has no prefers-reduced-motion check and no visibilitychange handler. Once an effect is on, its requestAnimationFrame loop runs for the entire session — including while the tab is in the background. On a phone carried around a factory floor that is continuous GPU work and measurable battery drain, and it ignores users who have asked their device for reduced motion.

I would fix this before adding effects, otherwise each new option multiplies an existing cost.

Proposed additions

Three that earn their place by matching a theme rather than just adding variety:

EffectReads asPairs withCost
Lưới kỹ thuật (blueprint grid)Slow-drifting technical grid, faint rulesIndustrialLow — static + slow offset
Quét màn hình (scanline)Single soft horizontal sweep, CRT bloomCyberpunkLow — one gradient band
Khối mờ (mesh gradient)Two or three large blurred colour blobs driftingLight / DarkLow — 3 arcs, heavy blur

All three are cheaper per frame than the existing particles effect, which animates 40+ objects with per-frame collision checks. Each pulls its colours from the active theme's tokens rather than hardcoding, so they inherit whatever R4 settles on.

5R4 Cyberpunk and Light contrast

Measured against WCAG 2.1 — 4.5:1 for text, 3:1 for the boundary of an interactive component. Both themes have real failures, and a third theme you did not ask about is worse than either.

Industrial is worse than either theme you named

Checking all four themes for the same pair: white on the Industrial accent #E67E22 measures 2.85:1 — below even Cyberpunk's 3.90. Every primary button label in that theme is harder to read than the two you flagged. Worth folding into the same pass.

5.1 Primary button labels

The button component hardcodes text-white on the accent fill. That works for the teal accent and fails for the pink and orange ones:

ThemeAccent fillWhite labelNear-black label
Light / Dark#006D776.08 keep—
Cyberpunk#FF00553.90 fail5.08 use
Industrial#E67E222.85 fail5.69 use

Proposal: add an --accent-on token — the foreground colour for anything sitting on an accent fill — and let each theme set it. White for the teal themes, near-black for the vivid ones. This keeps Cyberpunk's hot pink and Industrial's orange exactly as designed; only the label colour changes. Darkening the fills instead would work numerically (#E30050 reaches 4.81) but would mute the two themes whose whole point is being vivid.

5.2 Input fields

Both themes fill inputs with a ~3% overlay on the card — 1.07:1, effectively invisible. No fill alpha reaches 3:1 without looking like a grey block, so the boundary has to carry it. Proposal: keep the soft fill and add --border-strong, used on inputs, selects and other interactive edges:

TokenUsed forLightRatio vs card
--border-mainDecorative dividers, card hairlines#E2E8F0 unchanged1.23 fine
--border-strong newInput, select, and other interactive edges#7E8C9E3.42 clears 3

Splitting the token matters: WCAG's 3:1 rule applies to boundaries a user needs in order to identify a control, not to every hairline. Darkening --border-main globally to satisfy it would make every card edge heavy for no accessibility gain. Note that nothing between #E2E8F0 and #8A98A8 reaches 3:1 — #8A98A8 is still only 2.94 — so an interactive border has to be decisively darker; there is no subtle value that qualifies.

5.3 Colour coordination

This is where the two themes differ most, and it is not a contrast problem:

Light — coherent

One hue family

Body 215°, muted 215°, border 214°, accent 185°.

A 30° spread across the whole palette. Nothing to fix here beyond 5.2 — the coordination is already good.

Cyberpunk — competing

Two saturated hues, no neutral

Body 184°, everything else 340° — a 156° split, both at 100% saturation.

Worse, --border-main and --accent are the same value, so every hairline shouts as loudly as the primary action.

Proposal for Cyberpunk: give it the neutral it currently lacks, so pink can mean "this is the action" again.

  • --border-main #FF0055 → #4A3760 — a desaturated violet that sits in the same family without competing. Dividers recede; pink is reserved for accents.
  • --border-strong #6B4A8A for input edges — visible without being another pink.
  • Optional, subjective: soften body text from #00F0FF toward #8FE3EC. Contrast barely moves (13.51 → 13.02) but 100%-saturation cyan on near-black halates, which is tiring over a long shift. This changes the theme's character, so it is your call rather than mine.
